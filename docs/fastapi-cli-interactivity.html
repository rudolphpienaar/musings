FastAPI services that give you a CLI over HTTP

You asked for something in code, close to mush (the input interactive shell) and rcli (the reverse interactive shell): a FastAPI service that takes shell commands as jobs, delivers files into a run, offers a live prompt, and rendezvous through a mailbox a separate executor polls. Here is what actually exists — project by project, endpoint by endpoint.

No single project combines all four.

The pieces exist, but in different codebases, and never together. AutoGDB has the exact mailbox — for GDB, not a shell. term-wrapper has the cleanest interactive prompt. agent-infra/sandbox has jobs, files and PTY sessions in one service, but executes directly with no polling executor. The combination itself appears to be novel.

The nearest matches, in code

One spotlight per piece of the puzzle — the four codebases the target would be assembled from, plus pfmdb, the FNNDSC precedent for exposing a CLI over HTTP.

CLOSEST TO (d) — THE ONLY EXACT MAILBOX FOUND

AutoGDB

(d) exact

An AI-assisted GDB debugging tool whose FastAPI server is purely a hub between an LLM agent and a GDB session. The instruction queue, the polling executor, and the callback result are all there — verbatim the musings rendezvous shape — except the commands are GDB commands, there is no shell, no file delivery, and no interactive prompt (the GDB prompt is owned by the plugin; the agent never types into it).

1 · Agent submits & blocksPOST /instruct/?instruction=<gdb command> appends to instructions_queue (a FIFO list), then await_callback() polls results_dict every 3 s — with no timeout.
→
2 · Executor polls & runsThe GDB plugin (plugin/gpt.py, synchronous requests polling) calls GET /get-instruction → pop(0), or 404 if the queue is empty, and executes the command inside GDB.
→
3 · Result posted backPOST /see-callback/ {"instruction": str, "response": base64}. The server decodes base64, strips ANSI escapes, truncates output over 2,040 chars, stores results_dict[instruction] — and the blocked /instruct/ call returns it.
# also on the server GET /add-instruction/ GET /test-connection-gdb|cli GET / # HTML form for manual submission # deps: fastapi 0.108.0 · uvicorn 0.25.0 · httpx 0.26.0 uvicorn server.main:app --host 0.0.0.0 --port 5000

CLOSEST TO (c) — CLEANEST PTY API

term-wrapper

(c) strongest

PTY-based terminal emulation with a FastAPI backend (REST + WebSocket), a session manager, a Python CLI client and library, and an optional xterm.js frontend. Tested with bash, the Python REPL, vim / less / nano, htop, and the claude CLI.

POST /sessions {"command": ["python3", "examples/simple_tui.py"], "rows": 24, "cols": 80} → {"session_id": "…"} GET /sessions/{id}/output # raw GET /sessions/{id}/screen # parsed 2D buffer POST /sessions/{id}/input {"data": "+"} POST /sessions/{id}/resize DELETE /sessions/{id} WS /sessions/{id}/ws

The Python client mirrors it: create_session(command=["bash"]), write_input(session_id, "ls -la\r"), get_output(…, clear=True), get_text(strip_ansi_codes=True), wait_for_text, wait_for_quiet, get_new_lines / mark_read.

The catch for (d): the server owns and runs the PTY; the client polls the output. That is output-polling, not an executor polling a mailbox. And there is no file-delivery endpoint.

FIT(a) Session only(b) No(c) Yes(d) No

Source: PyPI — term-wrapper 0.7.4 (index); source named in PyPI text: github.com/rom1504/term-wrapper.

CLOSEST OVERALL — (a) + (b) + (c) IN ONE SERVICE

agent-infra/sandbox

3 of 4

An all-in-one AI-agent sandbox — browser, shell, file, MCP, VS Code server, Jupyter, terminal — in a single container, with a REST API implemented as FastAPI (OpenAPI). Persistent PTY sessions with stdin write and SSE streaming, plus real file upload/download.

# shell POST /v1/shell/exec POST /v1/shell/view POST /v1/shell/sessions/create GET /v1/shell/sessions POST /v1/shell/write # stdin POST /v1/shell/kill # file POST /v1/file/read|write|replace|search|find|list POST /v1/file/upload # multipart GET /v1/file/download

Text and base64 binary files, with streaming upload/download. The one missing piece is (d): the server executes directly; the client polls or views session output. There is no separate executor process polling a mailbox.

FIT(a) Yes(b) Yes(c) Yes(d) No

FNNDSC — LITERAL “CLI OVER HTTP” IN FASTAPI

FNNDSC/pfmdb

(a) partial

“A FastAPI interface to pfmongo — API endpoints mirror pfmongo CLI groups and subgroups.” A FastAPI REST service over a Mongo server, bundled with mongo + mongo-express, on :8025 with Swagger at :8025/docs. Last commit shown 9 Dec 2024; 0 stars.

POST /pfmongo/cli/{cmd} cmd: str = Path(..., encode_value_as_path=True) query: database, collection, handler = "smash" | "smashes" → await pfmdb_controller.cmd_exec(cmd, database, collection, handler) → SmashesResponse # “smash” = internal calls · “smashes” = remote IPC # to an embedded smash server — same request, sync

Plus REST mirrors of the CLI groups: GET /pfmongo (databases), GET/DELETE /pfmongo/{database}, …/{collection}, …/{document}, POST /pfmongo/{database}/{collection}/search, and GET /help (the pfmongo --help).

It is the closest literal precedent for “expose a CLI over HTTP” — but the CLI is only pfmongo: synchronous, no shell, no prompt, no queue, no polling, no file-into-run endpoint in the router inspected (File / UploadFile / FileResponse are imported, but the routes shown are DB CRUD / search / cli / help).

FIT(a) pfmongo only(b) No(c) No(d) No

Sources: github.com/FNNDSC/pfmdb and its router file — both verified live 2026-10-29.

CLEANEST ONE-SHOT SHELL ENDPOINT

host-terminal-mcp

(a) one-shot

An MCP server for running host terminal commands (originally for Claude), with an alternative FastAPI HTTP transport — http_server.py and an executor.py built on asyncio subprocesses. Permission modes: allowlist / blocklist / ask.

POST /execute {"command": "docker compose ps", "working_directory": "/path/to/project"} → {status, stdout, stderr, exit_code, timed_out, truncated, working_directory} GET /health POST /cd GET /cwd GET /permissions

Fully synchronous and one-shot: no persistent prompt (only cd / cwd state persists), no files, no mailbox. It is the tidiest reference for the single POST /execute shape, and nothing more.

FIT(a) Yes, one-shot(b) No(c) No(d) No

What the target would be assembled from

The report’s synthesis: the combination looks novel, but every individual mechanism has a working reference implementation.

(d) ← AutoGDBQueue / poll / callbackThe mailbox shape itself: FIFO instruction queue, executor polling, base64 result posted back.
(c) ← term-wrapperSession / input / output PTY APIPOST /sessions, POST …/input, GET …/output and …/screen, over REST + WebSocket.
(b) ← agent-infra/sandboxFile upload / downloadMultipart POST /v1/file/upload and GET /v1/file/download alongside the shell API.
(a) ← host-terminal-mcpPOST /executeThe one-shot shell job endpoint, returning stdout, stderr and exit code.

Two FNNDSC precedents complete the picture: pfcon’s zip-in / zip-out is the file-delivery precedent from your own ecosystem (submit a job, get results back as an archive — but Flask, not FastAPI), and pfmdb’s POST /pfmongo/cli/{cmd} is the precedent for exposing a CLI verbatim over HTTP — one product’s CLI, synchronously.

Excluded — and what could not be verified

Deliberately not counted

  • Generic web terminals — not FastAPI services: ttyd, wetty, Jupyter, code-server, Portainer. No FastAPI reimplementation of them was found that adds (a)–(d).
  • FastAPI dev CLIs: fastapi-mongo-setup (scaffolds FastAPI + Mongo projects, with interactive setup prompts) and the fastapi / fastapi-cli tooling family are CLIs for developing FastAPI apps — not services providing CLI interactivity over HTTP.
  • Container-local shells: just shell (the Django Python REPL in ChRIS_ultron_backEnd) is a local shell, not an HTTP service.
  • A generic FastAPI job POST — POST http://127.0.0.1:8000/job {"command": "echo \"Hello World\""} to a dispatcher whose worker nodes run it — is a plain job queue, not CLI interactivity, and was excluded as prior art.
  • WebShell (SudevOP1) describes itself as a “Web SSH Terminal (PTY) + Job Runner” with FastAPI + pty/ptyprocess + xterm.js + saved jobs, but is framed as a 6–8-hour timeboxed goal/spec. Not cited as established prior art without reading its code.

Open questions — stated plainly

  • AutoGDB has no single verified repo URL. DeepWiki uses aixiao0621/AutoGDB, while its getting-started text gives github.com/retr0reg/AutoGDB — a fork/rename discrepancy. Re-check the repo before citing one canonical URL.
  • host-terminal-mcp org spelling is unverified. Latest PyPI text gives ankitag-in/host-terminal-mcp; older PyPI/Glama text gives ankitaa186 variants.
  • agent-infra/sandbox process boundary unverified: the DeepWiki source says the REST API is implemented as FastAPI, but the container also bundles VNC / VS Code / Jupyter / terminal components, so whether the in-container service is itself the FastAPI app was not verified from code.
  • FNNDSC coverage: org searches for pfmongo (2 repos: pfmongo, pfmdb) and repl (1 repo: chili) found nothing else; pman / pfcon are Flask-era. Whether any other FNNDSC service uses FastAPI for shell-like interaction remains open beyond those searches.
  • The headline is a negative result over the indexed web — FNNDSC org search (live) plus PyPI / GitHub / DeepWiki searches for FastAPI PTY, shell-over-HTTP, MCP tool servers and mailbox polling. Confidence is high within that searched surface, but a private or obscure repo could still exist. It is not a proof of non-existence.
