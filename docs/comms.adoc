= musings Communication Contracts

musings exists for parties that cannot reach each other directly. One side runs a service on hardware it controls; the other side, an agent or a human, can only make outbound connections, or can only post files and commands to a place it can reach. The service therefore offers two core contracts plus one extension, each suited to a different shape of interaction: a drop box for streaming files, an asynchronous job queue for batch work, and, as an extension, a synchronous rendezvous for interactive shell use. All share the same authentication, the same base directory, and the same notion of completion. Two shell clients provide the human-facing ends: `mush`, a shell over the job queue, and a Python rush client for the synchronous extension. This document describes the contracts as agreed; the machinery that implements them is described in `architecture.adoc`.

== The drop box

The original purpose of musings is the simplest core contract: a place an external party can deposit files into, which the owner of the service can then reach. An external analysis, or an agent, posts files through the file-save endpoint into the server's base directory, one file at a time, for as long as it has data to send. When the deposit is complete, the depositor calls the EOT endpoint. The server writes a bare EOT marker and exits. A downstream consumer -- a ChRIS workflow node in server mode, or a poll-mode plugin watching a remote instance -- observes the marker and continues. The files are the durable product; the marker is only the signal that no more will arrive.

The EOT endpoint does exactly one thing: terminate. It carries a payload model, a contract on what a valid termination request must look like, so that a generic or accidental POST cannot shut the server down. It performs no accounting. It does not count jobs, it does not index files, it does not build a manifest. Its only effects are the EOT marker and process exit. This narrowness is deliberate: completion in a dataflow graph is itself a file, and the endpoint that produces it should have no other behaviour to reason about.

== The job queue

The second contract is asynchronous and is meant for batch work. A client submits a job carrying a command string; the job waits in an in-memory queue; an agent-side poller claims the oldest queued job atomically, executes it, and posts the result back; the client inspects the job at leisure. Claiming is atomic so that two pollers cannot claim the same job, and a claim on an empty queue returns no content rather than an error. This contract suits work that does not need a human watching: pipeline steps, cron-driven runs, and ChRIS nodes that poll an external instance for their inputs. Its cost is latency and indirection: every turn is two requests, submit and fetch, and the submitter must poll for the result. That cost is acceptable for batch work and unacceptable for an interactive shell, which is why the extension exists.

Its interactive end is `mush`, described below: a shell whose lines become job submissions, for a human who wants the queue rather than the rendezvous.

== The mush shell

Mush is the shell over the job queue, the counterpart of the rush client over the rendezvous. The user believes they are on a shell, but in reality they are in a local read-eval-post loop: each line becomes a `POST /jobs` submission, and mush polls `GET /jobs/{jobId}` until the job succeeds or fails, then prints its stdout, its stderr, and a non-zero exit marker when the command failed. Where rush streams output as it is produced, mush shows results only when they arrive, because the queue has no stream to forward; where rush needs an attached executor, mush needs a running poller, and any poller will do, since the queue's executor is shared across submitters rather than paired with one shell.

The working directory is held client-side, as in rush: mush intercepts `cd` lines itself and updates its own record of the current directory. But the jobs API carries no directory field, so mush prefixes the directory onto each submitted command, and the server does not clamp it. The directory is therefore relative to the poller's working directory, not to the service base directory, and a command that depends on it depends on where the poller was started. Interrupting a wait abandons the wait, not the job: mush prints the job identifier, and the result can still be fetched later. With `--no-wait`, mush submits each line and prints its queued job identifier without waiting at all, which makes it a posting shell as well as a waiting one.

== The rush rendezvous

The extension, `rush`, is the synchronous complement of the job queue, and it is the contract the rush client speaks. The musings server hosts a `/rush` endpoint. Any client may attach to it as an executor: the agent in its sandbox, another container, a laptop, any place willing to run commands. A submitter posts a command string to the endpoint, and that request blocks until an executor runs the command and returns the result. One POST, one execution, the result in the response.

The blocking is in the rendezvous, not in the server. The server holds the submitter's request open with asynchronous handling, so a waiting request costs a suspended coroutine and not a stalled server, and executors attach through a long-poll or websocket connection and may run commands concurrently. What blocks is the pairing of one submitter with one executor and one result. If no executor is attached, the endpoint must fail fast rather than hang until a timeout: a submission with nobody to run it is an error, not a wait.

Because a hanging request meets timeouts at every layer of the chain -- the submitter's HTTP client, the server, any proxy between them -- the response is streamed rather than delivered whole. The executor forwards output as it arrives, chunk by chunk, and the server forwards each chunk down the submitter's open response as one JSON object per line, stdout and stderr tagged separately so the two streams do not mix. The final chunk is an execution envelope in the hostlib shape: whether the program ran and exited cleanly, its return code, its complete output, the host it ran on, and how long it took. A stream that ends with the envelope means the command finished; a stream that ends without one means the connection dropped and the outcome is unknown, possibly still running on the executor. That distinction is the reason the envelope exists: the client must never infer success from the absence of output.

Streaming also keeps the request alive. Proxy timeouts are generally idle timeouts, and arriving chunks reset them, so a long command survives as long as it keeps producing output. A command that produces nothing for a long time still risks a timeout; that is a property of the transport, not of the contract, and the asynchronous job queue remains the correct tool for work of that shape.

Executor selection is an open point in this contract. With one executor attached, selection is trivial. With several, the server must decide whether the first waiting executor takes the command or the submitter addresses an executor by name. The initial deployment has one executor, so the rule can be settled when the second one arrives.

== The rush client

The rush client is a Python program that offers a shell-like prompt. The user believes they are on a shell inside the container, but in reality they are in a local application, a read-eval-print loop, whose lines become `/rush` posts. Each line the user types is sent to the server, executed by an attached executor, and the output is printed as it streams back. Because the commands genuinely run on the executor's machine, the ordinary Unix vocabulary comes for free: `ls`, `cat`, `grep`, and everything else are real commands, not endpoints the server must implement one by one.

The only shell state that must be maintained is the working directory, and it is maintained by the client, not the server. The client intercepts `cd` lines itself, updates its own record of the current directory, and sends every other line together with that directory. The server clamps the working directory to the base directory, so a client cannot navigate its way out of the space the server was started to serve. Keeping this state in the client is what keeps the server stateless, which is what keeps it mortal: no sessions to expire, nothing lost if the server restarts, no collision if two clients connect at once.

The rush client lives in the musings repository, beside the existing command-line client and the poller, because it is protocol-coupled to the server: endpoint shapes, authentication, the working-directory field, and the streaming envelope all move together, and a separate repository would duplicate the HTTP and authentication code for no gain. It becomes a general tool only if the protocol ever stabilises enough for other services to speak it, and that is not the case now.

== Execution

Commands are executed through hostlib, a small dependency-free library for running one program and reporting what happened. Its result envelope -- status never inferred from output, the argument list actually executed, the return code, complete stdout and stderr read concurrently so neither pipe can deadlock the other, host facts, and timing -- is the envelope the `/rush` stream closes with. Its sink protocol, a handful of methods called as output arrives, is the bridge between a running command and the stream: a sink forwards each chunk to the server, which forwards it to the submitter.

hostlib is deliberately not a shell. It performs no pipes, no redirection, no globbing in its argument list; a command that needs those must be wrapped explicitly as a shell invocation, so that the shell's involvement is visible rather than implicit. That narrowness is the library's value, and it is left as it is. The decision of when to allow a shell -- wrapping an incoming command string for the shell, or splitting it into an argument list and running it directly -- belongs to musings, per endpoint, not to the library all its consumers share. The poller runs commands through hostlib as an explicit `sh -c` invocation, with a timeout and an output cap, under the same rule.

== The contracts together

The core contracts divide by interaction shape. The drop box moves files from an external party into a workflow, and EOT ends the transfer. The job queue moves batch commands through a poller, and the result arrives when it arrives; `mush` is its interactive end, for a human who wants the queue as a shell. `rush` is an extension, not a third core contract: it reverses the direction, letting a submitter ask an external executor to run a command and wait for it, and it exists for the shape where work cannot run inside the sandbox at all. The rush client is its interactive end, for a human who wants a shell with output as it is produced. A workflow that needs files uses the first; a workflow that needs batch compute uses the second; a human who wants a shell uses the second through `mush` or the extension through rush, depending on whether the result may wait or must stream. All are guarded by the same bearer token, and the token holder owns the executor's shell for as long as an executor stays attached -- which is the point of the service, and the reason the token is required from the start and never optional.
