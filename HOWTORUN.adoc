= How to Run the musings Server

This document gives step-by-step instructions for running the musings server locally, in Docker, and as a poller client.

== Prerequisites

* Python 3.11 or later.
* `pip`.

== 1. One-time local setup

=== 1.1. Clone the repository

----
git clone https://github.com/rudolphpienaar/musings.git
cd musings
----

=== 1.2. Create and activate a virtual environment

----
python3 -m venv .venv
source .venv/bin/activate
----

=== 1.3. Install dependencies and the application

----
pip install -r requirements.txt
pip install -e .
----

With uv instead, from the repository root:

----
uv venv
uv pip install -e .
----

Either install creates the same console scripts: `musings`, `musings-server`, `musings-poller`, `mush`, `rush`, and `musings-rush-executor`.

=== 1.4. Configure a token

The server refuses to start without `MUSINGS_TOKEN`. Generate one:

----
export MUSINGS_TOKEN=$(openssl rand -hex 32)
export MUSINGS_BASE_DIR=./data
----

For a persistent setup, copy `.env.example` to `.env` and fill it in. Never commit a real token.

== 2. Run the server

----
musings-server
----

Then visit:

* API root: http://127.0.0.1:8000
* Interactive API docs: http://127.0.0.1:8000/docs

By default the server listens on loopback only, on the port named by `MUSINGS_URL`. To reach it from another machine, through a router port forward or across a LAN, make that decision visibly at startup:

----
musings-server --public
----

The server alone only relays: it queues jobs, stores messages, and writes `/save` files, but it never executes a command. For single-machine use it can embed a poller, which makes this host the execution target for anyone holding the token:

----
musings-server --with-poller
----

Listening beyond loopback over plain `http` is refused: the bearer token would cross the network in the clear. Either make the service `https` (next section) or state the acceptance with `musings-server --public --insecure`.

== 2a. TLS with a private CA

A musings server is reached by one or two parties the operator already knows, on an address that usually has no DNS name, so a public certificate authority buys nothing. Mint a private one with the bundled script. It uses only `openssl`, writes everything to `~/musings/pki` (set `PKI_DIR` to change that), and never into the repository.

----
scripts/pki_make.sh ca
scripts/pki_make.sh server --san IP:<lan address>,IP:<public address>
scripts/pki_make.sh client --name <remote party>
scripts/pki_make.sh client --name $(hostname)
scripts/pki_make.sh show
----

The server certificate always names `localhost` and `127.0.0.1`, because an embedded poller dials loopback; add every other address a client will use with `--san`. The second `client` line is for this host's own clients, the embedded poller included, since under mutual TLS they must present a certificate like anyone else.

Then make `MUSINGS_URL` an `https` URL and point the server at its files. `MUSINGS_TLS_CLIENT_CA` is optional and turns on mutual TLS: every connection must present a certificate signed by the CA, so holding the token is no longer enough to reach a route.

----
MUSINGS_URL=https://127.0.0.1:8000/api/v1
MUSINGS_TLS_CERT=/home/me/musings/pki/server.pem
MUSINGS_TLS_KEY=/home/me/musings/pki/server.key
MUSINGS_TLS_CLIENT_CA=/home/me/musings/pki/ca.pem
MUSINGS_CA_CERT=/home/me/musings/pki/ca.pem
MUSINGS_CLIENT_CERT=/home/me/musings/pki/clients/<this host>.pem
MUSINGS_CLIENT_KEY=/home/me/musings/pki/clients/<this host>.key
----

The last three are client-side: `MUSINGS_CA_CERT` pins the server certificate to your CA, and the certificate pair is what this host's clients present. A remote party needs `ca.pem` plus its own pair, handed over a channel you trust, and confirms the CA fingerprint printed by `show` out of band. With curl that party speaks to the server as:

----
curl --cacert ca.pem --cert <name>.pem --key <name>.key \
  -H "Authorization: Bearer <token>" https://<public address>:<port>/api/v1/health
----

Lifetimes are deliberate: the CA lives ten years, the server certificate a year, a client certificate 90 days because its key sits on someone else's machine. Renewal is rerunning the `server` or `client` subcommand after removing the old files, then restarting the server or re-sending the pair.

== 2b. TLS with a public certificate (Let's Encrypt)

A private CA fails the moment the remote party sits behind a TLS-intercepting egress proxy, as sandboxed agents often do: the proxy terminates the client's TLS and verifies the server with public roots, so neither a pinned CA nor a client certificate ever reaches the server. The answer is a certificate from a public authority on a DNS name you control. Nothing in the server changes; only the files differ.

Three things outside the repository come first. Create an A record for the name (say `musings.example.org`) pointing at the public address. Forward public TCP port 80 on the router to port 8080 on the server host, which lets the ACME HTTP challenge be answered without root. Then install certbot as a user tool:

----
uv tool install certbot
----

Issue the certificate into a directory you own, so no root is involved anywhere:

----
certbot certonly --standalone --http-01-port 8080 \
  --config-dir ~/musings/acme --work-dir ~/musings/acme/work --logs-dir ~/musings/acme/logs \
  -d musings.example.org -m you@example.org --agree-tos --no-eff-email
----

Point the server at the result and drop mutual TLS, which a proxy cannot carry. `MUSINGS_URL` carries the DNS name, since a public certificate verifies by hostname, not by address:

----
MUSINGS_URL=https://musings.example.org:8888/api/v1
MUSINGS_TLS_CERT=/home/me/musings/acme/live/musings.example.org/fullchain.pem
MUSINGS_TLS_KEY=/home/me/musings/acme/live/musings.example.org/privkey.pem
# MUSINGS_TLS_CLIENT_CA, MUSINGS_CA_CERT, MUSINGS_CLIENT_CERT, MUSINGS_CLIENT_KEY: unset
----

A LAN usually cannot reach its own public address, so on the server host add `127.0.0.1 musings.example.org` to `/etc/hosts`. Local clients and the embedded poller then dial loopback under the right name, and the certificate verifies. The remote party needs only the URL and the token:

----
curl -H "Authorization: Bearer <token>" https://musings.example.org:8888/api/v1/health
----

Certificates from Let's Encrypt last 90 days. `certbot renew` with the same three directory flags renews anything within 30 days of expiry; run it from a user cron or systemd timer, keep the port 80 forward in place for it, and restart the server afterwards, since uvicorn reads the files once at startup.

== 3. Run the poller

The poller is the execution side of the job queue, and starting it is the explicit grant of shell access: claimed commands run as the user it runs as, in the directory it runs in. In another terminal, with the same token and the service URL:

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<same token>
musings-poller
----

The poller claims work through a long-poll, so a freshly submitted job is claimed within a round-trip rather than a poll interval. Use `musings-poller --once` to check the queue immediately, execute at most one job, and exit.

== 4. Submit work

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<same token>
musings submit "df -kh" --description "disk check"
musings list
musings save reports disk.txt "report text"
musings eot --reason "all data delivered"
----

== 5. Run the interactive shell

For the shell feel over the job queue, with a poller running, run `mush`. Each line becomes a job and mush long-polls for its result, so output appears the moment the poller posts it. At startup mush warns immediately when no poller is attached, since without one every command queues forever. `mush --no-wait` submits without waiting.

For the same shell feel over the `rush` extension instead, attach an executor in one terminal. Attaching is the grant: by default the executor runs commands anywhere on its machine, starting in the directory it was launched from; `--clamp` confines them to `MUSINGS_RUSH_BASE_DIR` instead:

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<same token>
musings-rush-executor
# or, confined:
MUSINGS_RUSH_BASE_DIR=./data musings-rush-executor --clamp
----

In another, run rush:

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<same token>
rush
----

== 6. Docker

The image listens on every interface, as a container must, so it needs either TLS files mounted in and an `https` `MUSINGS_URL`, or an explicit `--insecure` when a TLS-terminating proxy sits in front of it. Plain:

----
docker build -t musings .
docker run --rm \
  -e MUSINGS_TOKEN=$(openssl rand -hex 32) \
  -e MUSINGS_BASE_DIR=/data \
  -p 8000:8000 \
  -v ./data:/data \
  musings musings-server --public --insecure
----

With the private CA from section 2a:

----
docker run --rm \
  -e MUSINGS_TOKEN=$(openssl rand -hex 32) \
  -e MUSINGS_BASE_DIR=/data \
  -e MUSINGS_URL=https://127.0.0.1:8000/api/v1 \
  -e MUSINGS_TLS_CERT=/pki/server.pem \
  -e MUSINGS_TLS_KEY=/pki/server.key \
  -e MUSINGS_TLS_CLIENT_CA=/pki/ca.pem \
  -p 8000:8000 \
  -v ./data:/data \
  -v ~/musings/pki:/pki:ro \
  musings
----

== 7. Run the tests

----
pip install pytest httpx
python -m pytest -q
----
