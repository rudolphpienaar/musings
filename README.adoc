== Abstract

Scientific workflows are multi-stage compute, usually represented as directed acyclic graphs (DAGs) and run as batch jobs: a node runs, its outputs materialize, and the next node consumes them. There is no user interface in that pattern and no interaction: nobody is watching, and nothing waits for a person.

But what if a stage needs one? A segmentation result needs a human approval before downstream stages may run. A stage needs ad-hoc files that only a human, or an agent acting for one, can generate on the fly: an approval, a missing input, a judgment call, a correction. Those needs do not fit a non-interactive pattern. The workflow either blocks forever waiting for something batch compute cannot produce, fails, or routes around the workflow entirely, and the provenance of the intervention is lost with it.

*musings* is one way, not the only way, to close that gap. It offers two shells into a batch process, in opposite directions. `mush`, the input interactive shell, pushes work in: at a prompt, each line typed becomes a job, and an agent-side poller claims jobs, executes them inside that instance, and posts structured results back. `rush`, the reverse interactive shell, pulls work out: a submitter, typically a process inside a closed sandbox, posts a signal to a mailbox; any attached executor polling the mailbox claims it atomically, runs it on its own machine outside the instance, and streams the output back, and the submitter's request blocks until that result arrives, or fails fast when no executor is attached. Nothing in `rush` forces the submitter to be inside and the executor outside: the server is only the rendezvous both sides dial out to, and the inside-outside split is the use case that makes it interesting, not a constraint of the code. Messages and files ride the same service: a message is a note read back through the API, a save is a durable file under the base directory. When transmission is done, an EOT signal writes an end-of-transmission (EOT) marker file into the output directory and the server exits. One use is as a workflow node: wrapped as a thin ChRIS plugin, musings is a node that waits for external input and then ends, so the dataflow graph continues -- the long standing problem of injecting external data into a workflow, reduced to one node with one contract: EOT means done.

== Introduction

=== What

musings is a FastAPI service with six capabilities:

* *Jobs.* An external entity submits a shell command (`POST /api/v1/jobs`). An agent-side poller claims the oldest queued job through a long-poll (`GET /api/v1/jobs/pending?wait=20`), so a fresh submission is claimed within a network round-trip rather than a poll interval, executes it, and posts a structured result -- exit code, stdout, stderr, timestamps, truncation flag (`POST /api/v1/jobs/{jobId}/result`). The server itself never executes anything: starting a poller is the deliberate act that grants execution, on the poller's machine, as the poller's user.
* *Mush.* The input interactive shell, over the job queue (`mush`): each line typed at the prompt becomes a job submission, and `mush` long-polls for its result, printing stdout, stderr, and a non-zero exit marker the moment the poller posts them. Its prompt shows the poller's real filesystem: at startup it learns the poller's working directory by running `pwd` through the queue, every `cd` is validated against the poller by running `cd <arg> && pwd` there, and the jobs API carries no directory field, so the resulting absolute path is prefixed onto each command.
* *Messages.* A plain information inbox (`POST /api/v1/messages`, `GET /api/v1/messages`) for unstructured notes alongside jobs. A message is a note to be read back through the API, not a file: it lives in memory, in submission order, and dies with the server restart.
* *Files.* An agent-to-user file path (`POST /api/v1/save`) that writes posted content to a directory and file under a configured base directory, with path traversal rejected. A save is a durable file on disk, not a note: a downstream workflow reads it from the filesystem, and EOT signals that no more files will arrive.
* *Termination.* An EOT signal (`POST /api/v1/eot`) that writes an EOT marker file into the base directory and then exits the process. The endpoint does only this, and its payload model -- `confirm` must be exactly `EOT` -- keeps a generic POST from shutting the server down. The service is mortal by design: it is born to serve one run, and it dies when that run is complete.
* *Rush (extension).* The reverse interactive shell. This is an extension, not the point of musings: it reverses the core direction, instead of bringing work into the sandbox. A mailbox (`POST /api/v1/rush`): a submitter, typically a process inside a closed sandbox, posts a signal there; any attached executor polling the mailbox claims it, runs it outside the instance, and streams the response back as JSON lines -- output chunks as produced, closed by an execution envelope. Executors claim work through a long-poll (`GET /api/v1/rush/next`), so they only need outbound connections. The submitter blocks until the result arrives, or fails fast when no executor is attached. The inside-outside arrangement is the use case, not a code constraint: the server is only a rendezvous both sides dial out to.

All protected routes require a bearer token (`MUSINGS_TOKEN`). A command-line client (`musings`), a server (`musings-server`), a poller (`musings-poller`), a shell-like rush client (`rush`), an input interactive shell (`mush`), and a `rush` executor (`musings-rush-executor`) ship in the repository.

=== Whoa -- security

Stated plainly, file injection and command execution is exactly the description that should alarm a security reviewer, and this section does not soften it. The controls are the answer to that alarm. The threat model is explicit: whoever holds the bearer token can execute shell commands as the user running the poller or any attached `rush` executor, and can write files under the base directory. Execution is opt-in by process: the server alone only relays and never runs a command, so the token becomes a shell only where someone deliberately starts `musings-poller` or an executor, and `musings-server --with-poller` is the explicit single-machine shorthand that makes the server host that target. Treat the token as a shell credential: generate it randomly, distribute it out of band (never in chat, never committed), rotate it on suspicion, and do not expose an unauthenticated instance to the public internet. Bearer tokens are only as safe as their transport, so put HTTPS in front of any publicly reachable deployment. The `/save` endpoint additionally confines writes to the base directory and rejects absolute paths and `..` components. The client tools deliberately bypass proxy environment variables (`trust_env=False`) because proxy parsing breaks in some sandboxed environments; proxy support is a roadmap item.

=== How

The interaction is a poll loop, chosen because the agent side can only make outbound connections. The service never calls the agent; the agent polls the service. The polls are long-polls: the server parks a claim request until a job is queued, and parks a result request until the result is posted, so waiting costs network round-trips, not poll intervals, and a prompt backed by a running poller answers in round-trips plus execution time:

----
submit job  ->  [queued]  ->  poller claims  ->  execute  ->  result posted
save file   ->  [base dir]                                     (file lands)
message     ->  [inbox]
rush        ->  [executor runs]  ->  streamed back            (one request)
eot         ->  [EOT written]  ->  process exits
----

Claiming is atomic: a job moves to `claimed` before it is returned, so two pollers never execute the same job. The EOT marker is written last, after all files are flushed, so a downstream consumer that sees EOT knows the output directory is complete. The marker is a file named `EOT` whose content is only a status and a reason; its presence is the signal, and it carries no job or file accounting.

=== Why

Musings exists for one gap in an otherwise batch-driven world. Scientific workflows are multi-stage compute represented as DAGs: each node runs, its outputs materialize, and the next node consumes them. There is no user interface in that pattern and no place for a person to intervene.

A sandbox is that pattern taken to its limit: closed by design. Nothing can reach into it -- no inbound network path, no webhooks, no pushed files, no interactive login -- and in a regulated setting that closure is a feature, not a bug. But a closed system still needs outside help, and it needs that help in a regulated fashion: only outbound connections from the sandbox, one bearer token, writes confined to a base directory, and a server that dies on EOT instead of lingering.

The sandboxed party is the obvious use case, not the boundary of the service. Anything that needs files injected or commands executed from outside, through a channel it controls, fits the same pattern; the sandbox is simply where the need is sharpest, because nothing else can reach in at all.

The help takes three shapes, and musings serves all three through the same channel. An external agent -- human or LLM -- intervenes deus ex machina, from outside a system that cannot be opened.

First, external files in, and approval. A workflow needs files it does not have: a missing input, an approval, a judgment call, a dataset held elsewhere. The canonical example is a segmentation result that needs a human approval before downstream stages may run: approval is not something batch compute can produce, so it must arrive from outside. The external agent saves files to a running instance and signals completion with EOT, and the workflow consumes what landed. A workflow node waiting on external data is one instance of this shape, not a separate purpose.

Second, external manipulation of internal files. Sometimes the files already exist inside, and the outside party needs to change them: edit a configuration, patch a script, reorganize an output directory. The same channel carries that work -- files written under the base directory, commands executed against them by the poller, results posted back -- without opening the sandbox itself.

Third, an external process, run and monitored from inside. Sometimes the work cannot run inside the sandbox at all: a tool, a license, a dataset, or a machine that lives elsewhere. The closed system then needs to reach out, not only to be reached. The `rush` rendezvous, the reverse interactive shell and a mailbox, serves that shape: a submitter inside asks an external executor to run the process, watches its output as it is produced, and ingests the results and files back through the same regulated channel. This is the reverse direction, and it is why `rush` exists, even though it is an extension to the core rather than the core itself.

* https://airflow.apache.org[Apache Airflow] sensors: the established pattern of a workflow node that waits on an external condition before letting the graph proceed. musings applies the same idea to human and agent input, with EOT as the condition.

== Installation (Methods)

Prerequisites on every platform: Python 3.11 or later, and `pip`. With uv instead, `uv venv` followed by `uv pip install -e .` installs the same console scripts (see link:HOWTORUN.adoc[HOWTORUN]). The server refuses to start without `MUSINGS_TOKEN` set.

=== Linux

----
git clone https://github.com/rudolphpienaar/musings.git
cd musings
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip install -e .
----

Run it (see link:HOWTORUN.adoc[HOWTORUN] for the full guide):

----
export MUSINGS_TOKEN=$(openssl rand -hex 32)
export MUSINGS_BASE_DIR=./data
musings-server
----

=== macOS

Identical, except for obtaining Python (via Homebrew or python.org) and creating the environment:

----
brew install python
git clone https://github.com/rudolphpienaar/musings.git
cd musings
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
pip install -e .
export MUSINGS_TOKEN=$(openssl rand -hex 32)
musings-server
----

=== Termux (Android)

Termux has no systemd and background processes are subject to Android's battery management, so run the server in the foreground (or under `termux-wake-lock`):

----
pkg update && pkg install python
git clone https://github.com/rudolphpienaar/musings.git
cd musings
pip install -r requirements.txt
pip install -e .
export MUSINGS_TOKEN=$(openssl rand -hex 32)
musings-server
----

The `musings` CLI, `musings-server`, `musings-poller`, `rush`, `mush`, and `musings-rush-executor` also run under Termux, which makes a phone a usable submission and polling station.

=== Docker

----
docker build -t musings .
docker run --rm \
  -e MUSINGS_TOKEN=$(openssl rand -hex 32) \
  -e MUSINGS_BASE_DIR=/data \
  -p 8000:8000 \
  -v ./data:/data \
  musings
----

Or with compose (see `docker-compose.yml`):

----
export MUSINGS_TOKEN=$(openssl rand -hex 32)
docker compose up
----

== Usage (Discussion)

=== Configuration

The server and every client read their settings from the environment, and from a `.env` file in the current working directory when one exists. A variable already present in the environment is never overwritten by `.env`, and a missing `.env` file is silently ignored.

Generate a `.env` with a random token. The token authenticates every protected route, so it must not be shared or committed:

----
token=$(openssl rand -hex 32)
cat > .env <<EOF
MUSINGS_TOKEN=$token
MUSINGS_URL=http://127.0.0.1:8000/api/v1
MUSINGS_BASE_DIR=./data
EOF
chmod 600 .env
----

`MUSINGS_TOKEN` is required by the server, which refuses to start without it. `MUSINGS_URL` and `MUSINGS_TOKEN` are both required by the clients (`mush`, `rush`, the poller, the rush executor, and the CLI), which exit when either is unset. `MUSINGS_URL` is the one source of truth for where the service lives on its machine: the clients connect to it, and the server listens on its port. Which interfaces the server listens on is not a setting but a startup decision: `musings-server` listens on loopback only, and `musings-server --public` listens on every interface, which is what a router port forward or a LAN client needs. The address a remote client uses (a public IP, a tunnel, a hostname) is a fact about the network in front of the server, not something the server is told; a LAN usually cannot reach itself through its own public address, which is why the local URL stays loopback and the public one lives only with the remote client. The server writes `/save` files under `MUSINGS_BASE_DIR` (default `./data`). `POLL_WAIT_SECONDS` (default 20, capped at 30 by the server) is how long the poller's claim long-poll parks before returning empty and polling again, and `POLL_INTERVAL_SECONDS` is its error backoff. The full set of variables with their defaults is in `.env.example`.

A `.env` file is read only from the directory the process runs in, so a client started elsewhere needs its own `.env` there or the variables exported explicitly. `.env` is gitignored and excluded from the Docker build by `.dockerignore`, and must never be committed: whoever holds the token holds the shell.

=== Endpoints

All routes live under `/api/v1` except the public root. Every route except `GET /` and `GET /api/v1/health` requires `Authorization: Bearer <token>`.

|===
| Method & path | Purpose

| `GET /` | Service info (public).
| `GET /api/v1/health` | Health check (public).
| `POST /api/v1/jobs` | Submit a command. Body: `command`, `description`, `timeoutSeconds`.
| `GET /api/v1/jobs` | List all jobs.
| `GET /api/v1/jobs/pending` | Atomically claim the oldest queued job. With `wait` (seconds, capped at 30) the request parks until a job arrives; 204 when the wait expires with the queue still empty. Every call stamps poller presence.
| `GET /api/v1/jobs/poller` | Report whether a poller has claim-polled within the presence window, and how long ago. Advisory: submissions queue either way.
| `GET /api/v1/jobs/{jobId}` | Fetch one job with its result. With `wait` (seconds, capped at 30) the request parks until the result lands or the wait expires, then returns the job as it stands.
| `POST /api/v1/jobs/{jobId}/result` | Post an execution result. 409 unless the job is claimed.
| `POST /api/v1/messages` | Post a message to the inbox.
| `GET /api/v1/messages` | List messages in submission order.
| `POST /api/v1/save` | Save content to `dir`/`file` under the base directory. Traversal outside the base is a 400.
| `POST /api/v1/rush` | Post a signal to the mailbox; the request blocks until an attached executor claims it, runs it outside the instance, and streams the response back as JSON lines closed by an execution envelope. 503 when no executor is attached.
| `GET /api/v1/rush/next` | Executor long-poll: claim the next pending submission. 204 when the wait expires with nothing pending.
| `POST /api/v1/rush/{submissionId}/chunk` | Executor post: one output chunk for a claimed submission.
| `POST /api/v1/rush/{submissionId}/result` | Executor post: the final execution envelope for a claimed submission.
| `POST /api/v1/eot` | Write the EOT marker file and exit. Body must confirm with `confirm: "EOT"`.
|===

=== The bidirectional loop

From the submitting side:

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<token>
musings submit "df -kh" --description "disk check"
musings list
musings get <jobId>
musings save reports disk.txt "disk report text"
musings eot --reason "all data delivered"
----

From the agent side, the poller runs the loop:

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<token>
musings-poller            # loop forever
musings-poller --once     # one job, then exit (cron-friendly)
----

Starting the poller is the explicit grant of execution, and that explicitness is the design, not an inconvenience: the server is only the rendezvous, so a running server exposes nothing but a queue, and commands gain a place to run exactly when, and exactly where, someone starts a poller. The poller claims through a long-poll (`POLL_WAIT_SECONDS`, default 20), so a submission is claimed the moment it lands rather than on the next scheduled visit, and it executes each claimed command as the user it runs as, in the directory it runs in.

For single-machine use, where the rendezvous and the execution host are deliberately the same box, the server can embed a poller:

----
musings-server --with-poller
----

This is a convenience with a stated cost: the server host becomes the execution target, and whoever holds the token can run commands there. Without the flag, the server only relays.

=== The input interactive shell (mush)

For a human at a prompt who wants the job queue, not the `rush` rendezvous, `mush` is the input interactive shell, a shell over `POST /api/v1/jobs`. Each line typed at the prompt becomes one job; `mush` long-polls `GET /api/v1/jobs/{jobId}?wait=10` until the job succeeds or fails, then prints its stdout, its stderr, and a non-zero exit marker when the command failed. The server parks each wait and answers the moment the result is posted, and the poller claims through its own long-poll, so with a poller attached the prompt answers in round-trips plus execution time, not poll intervals. It needs a running poller, not an attached `rush` executor, and it shows results only when they arrive, rather than streaming them as they are produced. At startup `mush` asks `GET /api/v1/jobs/poller` whether a poller is attached and warns immediately when none is, because a submission without a poller queues forever; a job still queued after 10s draws the same warning.

The prompt is honest about where it is. Where `rush` shows a pseudo-root confined to its base directory, `mush` has no confinement to display, so it shows the poller's real filesystem instead: at startup it learns the poller's working directory by running `pwd` through the queue, and every `cd` is validated by running `cd <arg> && pwd` there, so the prompt moves only where the poller can actually go and always displays the real absolute path. A failed `cd` prints the shell's error and leaves the prompt where it was, and a bare `cd` goes to the poller's home, as in a shell. When the directory cannot be known (no poller attached yet, or `--no-wait`, where results never come back) the prompt shows `?` rather than pretending. The jobs API carries no directory field, so the absolute path is prefixed onto each submitted command as a `cd`. Interrupting a wait abandons the wait but prints the job identifier, so the result can still be fetched later with `musings get`. With `--no-wait`, `mush` submits each line and prints its queued job identifier without waiting:

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<token>
mush
mush:/home/alice/run$ ls
mush:/home/alice/run$ cd reports
mush:/home/alice/run/reports$ cat disk.txt
mush:/home/alice/run/reports$ quit
----

=== The reverse interactive shell (rush, an extension)

Rush is an extension, not the point of musings. Where jobs and mush bring work into the sandbox, rush reverses the direction. The rendezvous is a mailbox: a submitter, typically a process inside a closed sandbox, posts a signal there, and any attached executor polling the mailbox claims it atomically, runs it on its own machine, and streams the output back. The submitter blocks until the result arrives, or fails fast when no executor is attached. The roles are symmetric in code. Nothing forces the submitter to be inside a sandbox and the executor outside it; the server is just the rendezvous both sides can dial out to. The interesting case is the one above: an inside process cannot reach an outside machine directly, so it asks through the mailbox instead. For a human at a prompt, the job queue's two-step turn is the wrong shape for that direction. The `rush` rendezvous is one POST per command, with output streaming back as it is produced. An executor attaches from wherever commands should run -- a container, a laptop, an agent sandbox -- and the rush client provides the shell experience:

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<token>
export MUSINGS_RUSH_BASE_DIR=/work
musings-rush-executor     # attach; commands are confined to /work
----

----
export MUSINGS_URL=http://127.0.0.1:8000/api/v1
export MUSINGS_TOKEN=<token>
rush
musings:/$ ls
musings:/$ cd reports
musings:/reports$ cat disk.txt
musings:/reports$ quit
----

Rush holds the working directory and intercepts `cd` itself; every other line is sent with the current directory, and the server clamps it to the base. Because commands genuinely run on the executor's machine, the ordinary Unix vocabulary comes for free. See link:docs/comms.adoc[the communication contracts] for the full design, including the streaming envelope and the fail-fast rule when no executor is attached.

=== The ChRIS mortal mode

Wrapped as a thin plugin, the service base directory is the plugin output directory. The workflow runs the plugin node; the node serves until an external entity sends the EOT signal; the EOT marker lands in the output directory; the process exits; CUBE harvests the outputs; the DAG continues. Downstream nodes gate on the EOT file. If the external data never arrives, the plugin wrapper's wait timeout (a wrapper parameter, not a server feature) must end the node visibly instead of stalling the DAG -- see link:docs/roadmap.adoc[the roadmap].

=== Limitations

* Job and message state is in process memory: restarting the server loses the queue. Persistent history is a roadmap item.
* A claimed job whose poller dies stays claimed; there is no claim expiry or requeue yet.
* A per-job `timeoutSeconds` is accepted and stored, but the poller and the `rush` executor currently run every command with `JOB_TIMEOUT_SECONDS` (default 300), not the per-job value.
* The poller executes commands as the user it runs as, with no allowlist and no sandboxing of its own. An allowlist is a roadmap item.
* Client proxy support is absent (see Whoa -- security above).
